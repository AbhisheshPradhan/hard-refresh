Synchronising with the world outside React, and the many times you should not.

An effect connects a component to something React does not control: a server, the document title, a browser API, a third-party widget. It runs after the commit, when the DOM is real (see 8).

That framing is the whole chapter. If nothing outside React is involved, an effect is usually the wrong tool, and most effect bugs are effects that should not exist.

## The dependency array

```jsx
useEffect(() => {
  // runs after commit
  return () => {
    // cleanup
  };
}, [id]);
```

| Second argument | When the effect runs |
|---|---|
| `[id]` | After this component's first commit, then whenever `id` changes |
| `[]` | After this component's first commit only |
| omitted | After every commit in which this component rendered |

Commit, not render, and the difference matters. A render can be thrown away — interrupted by an urgent update, superseded before it commits, or run a second time by StrictMode. Effects are attached during the commit and flushed after paint, so a render that never commits runs no effects at all. That is the same reason render must stay pure: work that might be discarded must leave no trace (see 8).

"After paint" is the default rather than the whole rule. When the update came from a discrete input event — a click, a keypress, a submit — React flushes pending effects synchronously before starting the next render, so that an effect scheduled by one click cannot still be waiting when the next one arrives.

Within a single commit there is a second ordering that explains some baffling bugs. React runs the cleanup for *every* effect in the tree before running the setup for *any* of them. Two passes, not one interleaved walk. So if two components subscribe to the same thing, both teardowns happen before either subscription is re-established — which is correct, and which surprises anyone expecting each component to tear down and set up as a unit.

"In which this component rendered" is the other half. If a memoized component is skipped, React never calls it, so its effects are not re-evaluated even though the app committed. This catches people who add `memo` for rendering cost and find the timing of their effects changed too (see 22).

React compares dependencies with `Object.is`, which for objects, arrays and functions means comparing identity rather than contents. Two objects with the same fields are different dependencies. This single fact causes most effect loops.

## Cleanup

The function you return runs before the effect runs again, and once more when the component unmounts. Not only on unmount — that is the common misreading, and it is why cleanup is what makes an effect correct rather than merely tidy.

```jsx
useEffect(() => {
  const onResize = () => {
    setWidth(window.innerWidth);
  };
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);
}, []);
```

Without the removal, every mount adds another listener and none are ever taken away.

## One job per effect

Effects are split by purpose, not bundled per component. Each gets the dependencies it actually needs, so unrelated things stop re-running together.

```jsx
const JobPage = ({ id }) => {
  useEffect(() => { … }, [id]);          // fetch the job
  useEffect(() => { … }, [job?.title]);  // set the document title
  useEffect(() => { … }, []);            // keyboard shortcut
};
```

## Effects that are not data fetching

Fetching gets the attention, but it is one case among several. Each of these is the same shape: subscribe, then unsubscribe in cleanup.

- Event listeners on `window` or `document`.
- `IntersectionObserver` for lazy images, impression tracking, infinite scroll (see 23).
- Writing to `localStorage` when a value changes.
- Timers and intervals.
- Mounting a non-React library into a DOM node, and destroying it on cleanup.

## Race conditions

```jsx
useEffect(() => {
  const controller = new AbortController();

  const load = async () => {
    try {
      const res = await fetch(`/api/jobs/${id}`, { signal: controller.signal });
      setJob(await res.json());
    } catch (err) {
      if (err.name !== 'AbortError') {
        setError(err);
      }
    }
  };

  load();
  return () => controller.abort();
}, [id]);
```

Cleanup aborts the previous request before starting the next.

The controller is created inside the effect body, so there is one per effect run, and the cleanup closes over its own. When `id` changes React runs that cleanup, `abort()` rejects the fetch it was tied to, the `await` throws an `AbortError` so `setJob` is never reached, and the `catch` recognises it and does nothing. Only then does the effect run again and create a fresh controller. Because the abort works by rejecting, `finally` runs on a cancelled request too — usually what you want, but worth being deliberate about. The alternative is an `ignore` flag set in cleanup, which lets the request finish but discards the result — use that when the response is worth caching or the request cannot be cancelled.

## When not to write an effect

Four options for producing a value, in the order you should consider them.

| Situation | Use |
|---|---|
| Value derives from props or state | Compute it during render |
| That computation is genuinely expensive | `useMemo` (see 22) |
| Something should happen because the user did something | An event handler |
| Something outside React must be kept in sync | An effect |

The most common mistake is the first row written as the last.

```jsx
// an effect and a second piece of state, for a value you already have
const [filtered, setFiltered] = useState([]);

useEffect(() => {
  setFiltered(jobs.filter((j) => j.type === type));
}, [jobs, type]);

// the same thing, computed during render
const filtered = jobs.filter((j) => j.type === type);
```

The effect version renders twice for every change — once with the old list, once after the effect sets state — and can show stale results in between. The second version cannot be out of date, because it is recalculated from the current values every time.

Related: to reset state when a prop changes, do not write an effect that calls a setter. Give the component a `key` and let React remount it (see 6, 9).

## Objects in the dependency array

This effect runs forever:

```jsx
const filters = { type, location };

useEffect(() => {
  fetchJobs(filters);
}, [filters]);   // new object identity on every render
```

The usual fix offered is `useMemo` on `filters`. It works, and it is treating the symptom. The object exists only to be passed to the effect, so the real question is why it is outside.

```jsx
useEffect(() => {
  fetchJobs({ type, location });   // built inside, depends on primitives
}, [type, location]);
```

Primitives compare by value, so the loop disappears with no memoization to maintain. Reach for `useMemo` only when the object is genuinely needed by several consumers, or when building it is expensive.

## useLayoutEffect

Same API, different timing: it runs inside the commit, after React has updated the DOM but *before* the browser paints. That makes it the tool for measuring a node and adjusting it in the same frame, so the user never sees the intermediate position — positioning a tooltip that would otherwise flash off-screen, for example.

It blocks painting, so it is the more expensive choice and not the default. If the user cannot see the difference, use `useEffect`.

### Why one flickers and the other does not

The difference is what happens when the effect sets state. A layout effect runs while React still has control, so React flushes the resulting render and commit synchronously before handing the frame to the browser. A passive effect runs after the paint, so its update is an ordinary one — a second render, a second commit, and a second frame the user can see.

Two costs follow. Work inside a layout effect delays the frame, so anything slow there is a dropped frame rather than a slow effect. And setting state in one means React renders and commits twice before painting once, so the frame carries double the work — worth it to remove a visible jump, wasteful otherwise.

<Callout kind="predict">
**What happens when**

An effect depends on `[jobs]` and, inside, calls `setJobs` with a new array built from the old one. What happens?

An infinite loop. The effect sets state, the new array has a new identity, the dependency comparison fails, the effect runs again. The loop is a symptom: state that is derived from other state usually should not be state at all, and the fix is almost always to compute the value during render instead.
</Callout>

## Gotchas

- **Effects run after commits, not renders.** A discarded or interrupted render runs none — and a component skipped by `memo` does not re-evaluate its effects at all.
- **Cleanup runs before every re-run**, not only on unmount.
- **Aborting rejects the promise.** The `catch` still runs, with an `AbortError` — filter it, or cancelling a request on purpose shows the user a failure.
- **The effect callback cannot be `async`.** React expects nothing or a cleanup function; declare an async function inside and call it.
- **Inline objects, arrays and functions in the dependency array always differ.** Depend on primitives, or move the value inside.
- **An empty dependency array is a claim, not a shortcut.** It says the effect reads nothing that changes, and it is how stale closures happen (see 10).
- **Effects do not run on the server**, so anything inside one is skipped during server rendering.
- **Two effects running in development** means missing cleanup, not a StrictMode bug (see 10).

## Takeaways

- An effect synchronises with something outside React. If nothing external is involved, do not write one.
- Dependencies are compared by identity, which is why objects and functions cause loops.
- Cleanup runs before each re-run and on unmount; it is what makes subscriptions and requests correct.
- One effect per job, each with its own dependencies.
- Derived values belong in render. Responses to user actions belong in handlers.
- `useLayoutEffect` runs before paint and blocks it; use it only to prevent a visible flash.
