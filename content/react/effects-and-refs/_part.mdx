React's model is declarative: describe what the screen should look like for the current state, and React makes it so. An **escape hatch** is a deliberate step outside that model, for things React does not control.

Real applications cannot stay inside. They talk to servers, read from `localStorage`, listen for scroll, focus an input, measure a node, mount a charting library that wants a DOM element of its own. None of that is a function of state, and no amount of describing the UI will make it happen.

React's answer is not to pretend everything fits the model. It is to provide a small number of named exits, so that stepping outside is explicit and visible rather than smuggled into a render.

The word hatch is doing work. Each exit gives up a guarantee React was making for you. A ref will not re-render, so what is on screen can silently disagree with the value. An effect runs after the fact, can leak if it does not clean up, and can hold values from a render that finished long ago. You open a hatch to get something done, and then you come back inside.

<Callout kind="build">
**The escape hatches, correctly**

Add the features that need effects and refs, and resist adding effects that do not.

- Replace the hard-coded array with a fetch, handling loading, error and empty — and cancel in flight requests when the query changes.
- Focus the first field when the add-job form mounts.
- Extract `useDebounce` and use it so the search fires one request per pause rather than per keystroke.
- Extract `useJobs`, then notice what happens when two components call it.
- Audit every effect you wrote and delete the ones computing a value you could derive during render.

The last item is the one that matters. Expect to delete at least one.
</Callout>
