What actually happens between calling a setter and the screen changing.

## Four phases

Calling a state setter does not change the DOM. It starts a sequence of four phases, and almost every confusing React behaviour comes from mistaking one phase for another.

1. **Trigger.** Something schedules an update: a state setter, a parent re-rendering, or the initial mount.
2. **Render.** React calls your component function and collects what it returns. Nothing touches the DOM. This work can be paused, restarted, or thrown away.
3. **Commit.** React applies the differences to the real DOM. This phase runs to completion and cannot be interrupted.
4. **Effects.** After the browser paints, React runs your effects.

## Render asks, commit answers

When React renders your component, it is asking a question: given this state and these props, what should the UI look like? Your job is to answer it. Your job is not to make it happen.

JobListing.jsx

```jsx
const JobListing = ({ job }) => {
  const [showFull, setShowFull] = useState(false);

  const description = showFull
    ? job.description
    : job.description.substring(0, 90) + '...';

  return (
    <div className="bg-white rounded-xl shadow-md">
      <h3>{job.title}</h3>
      <p>{description}</p>
      <button onClick={() => setShowFull((prev) => !prev)}>
        {showFull ? 'Less' : 'More'}
      </button>
    </div>
  );
};
```

Click *More* and all four phases run. React re-renders `JobListing`, gets back a description with the full text, works out that one paragraph's text changed, writes that one change to the DOM, and paints. The `<h3>` is untouched because nothing about it changed.

## Render must be pure

Because render can run more than once and be thrown away, it has to be safe to run repeatedly. Same props and state in, same result out, and nothing else changed on the way.

Three things that break this rule, all of which look reasonable:

```jsx
const JobListing = ({ job }) => {
  // 1. mutating a prop
  job.title = job.title.toUpperCase();

  // 2. writing to something outside the component
  viewCount = viewCount + 1;

  // 3. doing work that should be an effect
  document.title = job.title;

  return <h3>{job.title}</h3>;
};
```

Each is a side effect: an observable change to the world that happens while React is only asking a question. Run the render twice and the title is uppercased twice, the count is wrong, and the document title is set during work React may discard.

The fixes follow from the phases. Derive values instead of mutating; put genuine side effects in an effect, which runs in phase four when the render is committed and real.

```jsx
const JobListing = ({ job }) => {
  const title = job.title.toUpperCase();   // derive, don't mutate

  useEffect(() => {
    document.title = title;            // side effect, after commit
  }, [title]);

  return <h3>{title}</h3>;
};
```

Three things fall out of the grid. State survives an update because the fiber is reused, and is lost on unmount because the fiber is discarded (see 9). Nothing in the middle row happens for a component whose output is unchanged, which is why a re-render need not touch the DOM at all. And every effect in the bottom row runs after the paint above it, which is why an effect can never prevent a flicker — the user has already seen the frame.

## Why you cannot read the DOM during render

During render, the DOM still shows the *previous* screen. The elements your component describes do not exist yet. So measuring during render gives you an answer from the past, or nothing at all.

```jsx
const JobDescription = ({ text }) => {
  const ref = useRef(null);

  // null on first render; stale on every render after
  const height = ref.current?.offsetHeight;

  return <p ref={ref}>{text}</p>;
};
```

Measuring belongs after commit, when the node exists (see 12 for refs, 11 for the effect that reads them).

<Callout kind="predict">
**What happens when**

You call `setShowFull(true)` inside a click handler, then read the DOM on the very next line to check the paragraph got longer. What do you see?

The old text. The setter schedules an update; it does not render synchronously. By the time your next line runs, phases two and three have not happened yet. This is the same reason reading the state variable straight after setting it gives you the old value (see 4).
</Callout>

## Where React ends and the DOM begins

React is split in two, and the split explains several things that otherwise look arbitrary.

The `react` package is the **public API**: `createElement`, context, the hook functions you import. It contains almost no machinery — `useState` there is a few lines that forward the call to whichever dispatcher is currently installed.

The **reconciler** — the part that knows about fibers, state, hooks and what changed — is a separate package, `react-reconciler`, and it ships bundled inside each renderer rather than standing alone. So the fiber hook implementations that make `useState` actually work live in `react-dom + reconciler`, not in `react`. A **renderer** is that reconciler plus a set of host operations: `react-dom` creates and patches browser nodes, `react-native + reconciler` creates native views.

The practical shape is still one reconciler and several renderers. It is just that the reconciler travels with the renderer rather than living in the package you import from.

main.jsx

```jsx
import { StrictMode } from 'react';           // the reconciler
import { createRoot } from 'react-dom/client'; // the renderer

createRoot(document.getElementById('root')).render(
  <StrictMode>
    <App />
  </StrictMode>
);
```

The same split explains events. React does not attach a listener to every button. `react-dom` attaches listeners at the root container and works out which component an event belongs to, which is why `e.stopPropagation()` behaves in terms of your component tree rather than the DOM tree (see 5). Where that distinction really bites is portals, whose DOM node sits elsewhere entirely while events still travel the React tree (see 25).

The root container, rather than `document`, is where those listeners live — a change made in React 17. Attaching at `document` meant two React versions on one page fought over the same listeners, so incremental upgrades and multiple independent roots on a single page were impractical. Moving to the container made both routine, which is why you will see older articles describing delegation at the document level.

## Gotchas

- **A render can happen without a commit.** If nothing changed, or the render was interrupted, React discards the work. Never assume rendering means the screen updated.
- **In development, StrictMode renders twice.** Two `console.log` lines from one click is not a bug. It is React checking that the component renders purely (see 10).
- **State setters do not render immediately.** They schedule. Several setters in one handler produce one render, not several (see 9 on batching).
- **Effects usually run after paint.** If an effect measures a node and repositions it, the user can see the first position briefly. Updates from discrete input events are the exception (see 11). That is the case `useLayoutEffect` exists for (see 11).
- **"Re-render" does not mean "DOM update".** React re-runs your function and compares; the DOM is only touched where something actually differs.

## Takeaways

- Trigger, render, commit, effects. Different phases, different rules.
- Render describes; commit applies. Only commit touches the DOM.
- Render can be paused or discarded, so it must be pure. Commit cannot be interrupted.
- The DOM during render is the previous screen. Measure after commit.
- `react` is the reconciler, `react-dom` is the renderer, and events are delegated at the root.
