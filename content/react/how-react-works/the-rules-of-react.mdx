React makes assumptions about the code you write in order to render it in pieces, reuse work, and skip components. Those assumptions are written down as rules. Break one and the failure usually shows up somewhere else entirely, which is why they are worth knowing as rules rather than rediscovering as bugs.

  Only call hooks at the top level of a component or another hook.
  Only call hooks from React function components or from custom hooks.
  Components and hooks must be pure: same inputs, same output, no side effects while rendering.
  Never mutate props, state, or values returned by hooks.
  Never mutate values after passing them to JSX.
  React calls your components and hooks. You do not call them yourself.
  Never pass a hook around as a value. Call it; do not store it, forward it, or choose one dynamically.

## Why hooks must be at the top level

React does not know hooks by name. Each fiber holds an ordered list of hook slots, and on every render React hands out the slots in call order: first `useState` gets slot one, the next hook gets slot two, and so on.

So the rule is really about keeping the call order identical on every render. A hook inside a condition, a loop, or after an early return changes the count, and every slot after it shifts.

```jsx
const JobFilters = ({ isLoggedIn }) => {
  if (isLoggedIn) {
    const [name, setName] = useState('');    // slot 1, but only sometimes
  }
  const [theme, setTheme] = useState('light'); // slot 1 or slot 2, depending
  …
};
```

What the rule forbids is a hook call that happens on some renders and not others. A condition *inside* a hook is fine, because the call itself is unconditional:

```jsx
if (isLoggedIn) {
  useEffect(() => {              // no — the call is conditional
    track(user.id);
  }, [user.id]);
}

useEffect(() => {                // yes — always called
  if (isLoggedIn) {
    track(user.id);
  }
}, [isLoggedIn, user.id]);
```

The reason is that a slot is claimed by the *call*, not by what happens inside it. React's bookkeeping counts hook calls and their order and nothing else — it never looks inside the function you pass. `useEffect` stores your callback in a slot and runs it later; whether that callback branches, returns early or does nothing at all is ordinary JavaScript React has no opinion about. The same holds for `useMemo` and `useCallback`: a condition inside the factory changes the value in the slot, not which slot it went to.

So the requirement is narrow: the same hooks, in the same order, on every render. Everything else is yours. Put the branch in the dependency array, in the value you return, or in the body of the callback — anywhere except around the call itself.

When you genuinely need a hook only some of the time, the component boundary is where conditionality is legal. Move the hook into its own component and render that component conditionally: `{isLoggedIn && }`. The hook is then unconditional within its component, and React mounts and unmounts the whole thing — which it is designed to do. People who learn the rule as "no conditions near hooks" end up writing far more awkward code than it asks for, and usually miss this option entirely.

The second rule follows from the same mechanism. Hook state lives on a fiber, and a plain function called outside rendering has no fiber, so there is nothing to store state on. Custom hooks work because React is still the one rendering the component that called them.

### Hooks are called, not passed

The same reasoning extends one step further. A hook must be called directly by name, not stored in a variable, passed as a prop, or picked from an object at runtime.

```jsx
// no: which hook runs is now decided at runtime
const useData = isRemote ? useRemoteJobs : useLocalJobs;
const jobs = useData();

// yes: both calls are unconditional and visible
const remote = useRemoteJobs();
const local = useLocalJobs();
const jobs = isRemote ? remote : local;
```

React and its tooling need to see which hooks a component calls, in a fixed order, by reading the code. A hook behind a variable is invisible to that analysis, so the linter cannot check it and the compiler cannot optimise around it.

## Purity

Given the same props and state, a component must return the same result, and must not change anything else on the way. This is not style advice. React may render a component twice, discard the result, or interrupt it partway (see 8, 9), so anything observable that happens during render happens an unpredictable number of times.

```jsx
let viewCount = 0;

const JobPage = ({ job }) => {
  viewCount++;                        // changes something outside
  job.title = job.title.trim();       // mutates a prop
  document.title = job.title;         // touches the world
  const id = Math.random();           // different output, same input
  …
};
```

Randomness and the current time belong in three places instead: a state initializer, an effect, or an event handler. All three run at moments when the result is real.

## Never mutate

Props, state and hook return values are read-only. The practical reason is identity: React decides what changed by comparing references, so a mutated array is the same array and nothing happens.

```jsx
const removeJob = (id) => {
  const index = jobs.findIndex((j) => j.id === id);
  jobs.splice(index, 1);     // same array reference
  setJobs(jobs);             // React sees no change: no re-render
};

const removeJob = (id) => {
  setJobs(jobs.filter((j) => j.id !== id));  // new array
};
```

The first version is worse than a no-op. The data has changed but the screen has not, so the two disagree until something unrelated triggers a render and the update appears late, seemingly at random.

## Stale closures

Every render creates fresh functions, and each one captures the values from the render that created it. Usually that is exactly right: a click handler should act on the state the user was looking at.

It goes wrong when a function outlives its render. Intervals, event listeners, timeouts and subscriptions are all set up once and then keep running with the values they captured.

```jsx
useEffect(() => {
  const id = setInterval(() => {
    setSeconds(seconds + 1);   // seconds is always 0 here
  }, 1000);
  return () => clearInterval(id);
}, []);
```

Four fixes, in order of preference. Use the functional update, `setSeconds((s) => s + 1)`, when the new value depends only on the old one — the interval no longer needs to know the value at all. Add the dependency and let the effect re-subscribe, when the effect genuinely differs per value.

Where neither works — the effect must read the latest value but must not tear down and rebuild when it changes — that is what `useEffectEvent` is for. It wraps the part that should always see current values, and that part is not a dependency:

```jsx
const onTick = useEffectEvent(() => {
  logProgress(seconds, filter);   // always the latest
});

useEffect(() => {
  const id = setInterval(() => {
    onTick();
  }, 1000);

  return () => {
    clearInterval(id);
  };
}, []);                           // no re-subscribing on every tick
```

Stable since React 19.2, and it supersedes the ref for this case. The constraints are strict — it may only be called from inside an Effect in the same component, and cannot be passed as a prop or returned from a hook — because React needs to know it never escapes (see the hooks appendix). Keep the ref as the fallback in codebases on older versions.

## StrictMode

In development, `StrictMode` deliberately calls your component functions twice, and mounts each effect, unmounts it, and mounts it again. None of this happens in production.

It is a purity test. If the second call produces something different, or the second mount leaves two of something running, the code was already broken and the double invocation made it visible now instead of intermittently later. An effect that survives being mounted twice is an effect with correct cleanup.

  
### What happens when

  
An effect opens a WebSocket and has no cleanup. What do you see in development under StrictMode, and what does it tell you about production?

  
Two open sockets. In production the effect mounts once, so it looks fine — until the component unmounts and remounts on a route change, and now there are two sockets in production too, with no way to close the first. StrictMode did not create the leak; it moved the discovery to the first minute rather than the first month.

## The linter

`eslint-plugin-react-hooks` enforces both hook rules and checks dependency arrays. Treat its warnings as errors rather than suggestions.

These rules also stopped being merely good practice. React Compiler memoizes your components automatically by reasoning about data flow, and that reasoning assumes the rules hold. Where it cannot prove a component is safe, it skips optimising it; where you break a rule in a way it cannot see, the output can be wrong. The rules are now the price of the free optimisation.

## Gotchas

- The rule is about the call, not the contents. A hook that runs on some renders and not others breaks the slot order; a condition inside the callback does not.
- An early return before a hook is the most common violation. A loading guard placed above useEffect looks harmless and breaks the slot order.
- Conditions inside a hook are fine. `useEffect(() => { if (x) … })` is legal; `if (x) useEffect(…)` is not.
- Custom hooks are hook calls. They obey the same two rules, including inside your own useJobs.
- A hook stored in a variable or passed as a prop defeats both the linter and the compiler, even if it happens to run correctly.
- Mutating state and calling the setter with the same reference does nothing. No warning, no render.
- Do not silence StrictMode's double effect with a ref guard. That hides the missing cleanup rather than fixing it.
- Math.random() and Date.now() during render are impure. In a state initializer, an effect or a handler they are fine.

## Takeaways

- Hooks are matched to stored slots by call order, which is the entire reason for the top-level rule.
- The slot belongs to the call, not its contents — so a condition inside a hook is fine, and a hook needed only sometimes belongs in its own component.
- Render may run more than once and be discarded, so it must be pure.
- Mutation defeats React's identity comparison: new value, new reference.
- Functions capture the render that made them. Anything long-lived captures the render it was created in.
- For a value an effect must read but not re-subscribe to, useEffectEvent is the current answer; a ref is the older one.
- StrictMode's double invocation is a purity and cleanup test, and is development-only.
- The linter enforces the contract, and the compiler now depends on it.
