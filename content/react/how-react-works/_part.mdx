With Part I you can build things. Shortly after that, React starts behaving in ways the API does not explain.

An input loses focus on every keystroke. A value read straight after setting it is one click behind. A component you never touched renders anyway, and one you expected to render does not. A console log appears twice. None of these are answerable from the documentation for the hook involved, because none of them are about the hook.

They are all consequences of three decisions React makes in order to keep the screen in sync with state without being slow. It works in separate phases rather than updating the DOM as it goes. It keeps its own copy of the tree so it can compare rather than rebuild. And it decides what to skip, pause and prioritise instead of doing everything immediately.

This part is those three decisions. It is placed here, rather than at the front, because the ideas only mean anything once you have written enough components to have been caught by them.

<Callout kind="build">
**Prove it to yourself**

Part II is explanation rather than API, so the exercise is instrumentation. Take the job board from Part I and make its behaviour visible.

- Turn on *Highlight updates* and type in the search box. Note every component that flashes and say why before checking.
- Add a `console.log` at the top of `JobCard`. Count the logs for one keystroke, then predict the count after wrapping it in `memo` — and explain the result if it does not change.
- Break it deliberately: define `JobCard` inside `JobList`, then type in a card's input and watch focus go.
- Put a `useState` inside an `if` and read the error carefully rather than reverting immediately.

The goal is that nothing in this part remains a claim you have only read.
</Callout>
