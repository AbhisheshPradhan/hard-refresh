The problems a store solves that Context does not, and the state that belongs in neither.

Chapter 14 ended with reducers and Context, which between them cover a lot. It is worth being precise about where they stop, because that is the entire case for a store.

| Limitation | What it looks like |
|---|---|
| No slice subscriptions | Every consumer re-renders on any change to the context value |
| Logic scattered across providers | Related updates live in different files with no shared shape |
| No devtools | You cannot see what changed, when, or replay it |
| Async has no home | Every provider invents its own loading and error handling |
| State tied to the tree | Reading or updating outside React is awkward |

Redux Toolkit is the modern, batteries-included Redux. It removes almost all the boilerplate the old Redux was known for.

## A slice

A slice bundles the state, the reducers and the generated action creators for one area of the app.

```jsx
import { createSlice } from '@reduxjs/toolkit';

const jobsSlice = createSlice({
  name: 'jobs',
  initialState: {
    items: [],
    filter: 'All',
  },
  reducers: {
    jobAdded: (state, action) => {
      state.items.push(action.payload);   // looks like mutation; it is not
    },
    jobDeleted: (state, action) => {
      state.items = state.items.filter((job) => job.id !== action.payload);
    },
    filterChanged: (state, action) => {
      state.filter = action.payload;
    },
  },
});

export const { jobAdded, jobDeleted, filterChanged } = jobsSlice.actions;
export default jobsSlice.reducer;
```

The mutation is the surprising part. Redux Toolkit runs reducers through Immer, which hands you a draft, records what you changed, and produces a new immutable state from it. You write mutating code; the store still gets a new object every time. The rule from chapter 10 has not been repealed — it has been automated, and only inside `createSlice`.

## The store

```jsx
import { configureStore } from '@reduxjs/toolkit';
import jobsReducer from './jobsSlice';

export const store = configureStore({
  reducer: {
    jobs: jobsReducer,
  },
});

// main.jsx
<Provider store={store}>
  <App />
</Provider>
```

## Reading and writing

```jsx
const JobList = () => {
  const jobs = useSelector((state) => state.jobs.items);
  const dispatch = useDispatch();

  return jobs.map((job) => (
    <JobCard
      key={job.id}
      job={job}
      onDelete={() => {
        dispatch(jobDeleted(job.id));
      }}
    />
  ));
};
```

This is the difference from Context in one line. `useSelector` subscribes to what the function returns, not to the whole store, so a component reading `state.jobs.filter` does not re-render when `items` changes.

### Selectors and identity

`useSelector` compares the previous and next results by reference. A selector that builds a new value every call therefore re-renders every time the store changes, whatever the data.

```jsx
// new array every call: re-renders on any store change
const remote = useSelector((state) => {
  return state.jobs.items.filter((job) => job.isRemote);
});

// memoized: recomputes only when items changes
const selectRemoteJobs = createSelector(
  [(state) => state.jobs.items],
  (items) => items.filter((job) => job.isRemote)
);

const remote = useSelector(selectRemoteJobs);
```

Select raw values where you can, and reach for `createSelector` when a derived value has to be computed.

## Async with thunks

```jsx
export const fetchJobs = createAsyncThunk('jobs/fetch', async () => {
  const res = await fetch('/api/jobs');
  return res.json();
});

// in the slice
extraReducers: (builder) => {
  builder
    .addCase(fetchJobs.pending, (state) => {
      state.status = 'loading';
    })
    .addCase(fetchJobs.fulfilled, (state, action) => {
      state.status = 'idle';
      state.items = action.payload;
    })
    .addCase(fetchJobs.rejected, (state, action) => {
      state.status = 'failed';
      state.error = action.error.message;
    });
}
```

One thunk generates three action types, and the slice handles each. Which is fine, and also the point at which to ask whether this belongs in Redux at all.

## Normalized state

An array is awkward for collections: updating one job means mapping the whole array, and finding one means scanning it. A normalized shape stores items by id.

```jsx
{
  ids: ['1', '2', '3'],
  entities: {
    '1': { id: '1', title: 'React Developer' },
    '2': { id: '2', title: 'Front-End Engineer' },
  }
}
```

Lookups and updates become direct key access, and there is exactly one copy of each job, so the same entity cannot appear twice with different data. `createEntityAdapter` produces this shape along with reducers and selectors for it.

```jsx
const jobsAdapter = createEntityAdapter();

const jobsSlice = createSlice({
  name: 'jobs',
  initialState: jobsAdapter.getInitialState(),
  reducers: {
    jobAdded: jobsAdapter.addOne,
    jobUpdated: jobsAdapter.updateOne,
    jobDeleted: jobsAdapter.removeOne,
    jobsLoaded: jobsAdapter.setAll,
  },
});

export const { selectAll, selectById } = jobsAdapter.getSelectors(
  (state) => state.jobs
);
```

## Server state is not Redux state

Most of what people put in Redux is a copy of data that lives on a server. That is not application state; it is a cache, and it has problems Redux does not address: when is it stale, when should it refetch, what happens when two components ask for the same thing, how is it invalidated after a mutation.

Thunks let you hand-write the loading and error handling for each case, which is why so many Redux codebases contain the same twenty lines repeated per resource. A query library handles all of it (see 16). RTK Query is the equivalent inside the Redux ecosystem, and is worth preferring if you are already using the store.

| State | Where it belongs |
|---|---|
| Jobs fetched from the API | A cache: TanStack Query or RTK Query |
| The current filter and sort | Component state, or the URL (see 17) |
| Which items are selected for bulk actions | Lifted state, or a store if it spans routes |
| Multi-step wizard progress | A reducer, in a store if several routes read it |
| Authenticated user | Context is usually enough (see 20) |

Once server data moves out, many apps discover they had very little global client state left — which is the honest answer to whether they needed Redux.

## When to use it

**Default:** do not add Redux to a new app. Start with colocated state, lift where needed, add a cache for server data, and use Context for the two or three genuinely app-wide values.

**Add it when** you have substantial client state that many parts of the app both read and write, with complex transitions worth expressing as actions — a spreadsheet, a builder, a multi-step configurator, an editor with undo. The devtools and the single audit trail of "what changed and why" become real advantages at that size.

<Callout kind="predict">
**What happens when**

A component uses `useSelector((state) => state.jobs.items.filter(isRemote))`, and an unrelated part of the store changes. What happens?

It re-renders. The selector runs, `filter` returns a new array, and the reference comparison fails even though the jobs are identical. Wrap it in `createSelector`, or select `items` and filter in the component — where the array is recreated too, but at least no subscription is triggered by it.
</Callout>

## Gotchas

- **Immer's draft mutation only works inside `createSlice` and `createReducer`.** Elsewhere the old rules apply.
- **Do not return *and* mutate in the same reducer.** Do one or the other.
- **A selector returning a new object or array re-renders on every store change.** Memoize or select raw values.
- **Non-serializable values in the store** — dates, class instances, functions — break devtools and time travel, and the middleware will warn.
- **Putting fetched data in Redux by default** is the most common way a store grows into something nobody wants to maintain.
- **A store does not remove the need for good placement.** Component state is still correct for most values.

## Takeaways

- Redux exists for slice subscriptions, one place for update logic, devtools, and a home for complex transitions.
- `createSlice` generates the reducer and the action creators; Immer makes mutating syntax safe inside it.
- `useSelector` subscribes to a slice; results are compared by reference, so derived values need `createSelector`.
- Thunks handle async, and produce pending, fulfilled and rejected actions.
- Normalized state makes lookups and updates direct; `createEntityAdapter` builds it for you.
- Server data is a cache, not application state. Move it out and re-ask whether you need a store at all.
