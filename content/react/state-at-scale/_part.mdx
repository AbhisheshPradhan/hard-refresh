Everything so far has kept state inside the component that uses it. This part is about what happens when more than one component needs the same value.

The question sounds like a tooling question — Context or Redux? — and it almost never is. Most state problems are placement problems. A value sits too high and re-renders half the app on every keystroke, or too low and has to be threaded through six components that do not care about it, or it is stored in two places that drift apart.

So these chapters work outward. Where should a value live, given who reads it? What do you do when updates get complicated enough that scattered setters stop being readable? What does Context actually solve, and what does it quietly cost? And when is a store worth its weight?

<Callout kind="build">
**Place the state deliberately**

No new features. Re-place what you already have and justify each decision out loud.

- Move each piece of state to the lowest component that needs it, and note where that stops being possible.
- Add a saved-jobs feature shared by two distant components, using context.
- Split that context so a fast-changing value does not re-render consumers of a slow-changing one.
- Convert the add-job form to `useReducer` and decide afterwards whether it was worth it.
- Add undo to the job list with past, present and future stacks.

Then answer the question a reviewer would ask: which of this state is server data pretending to be client state?
</Callout>

<Callout kind="note">
**By the end of this part**

You should be able to place a piece of state deliberately and say why, diagnose re-render problems that come from placement rather than rendering, and give a straight answer to "should this go in Redux" — including the cases where the honest answer is that it is server data and belongs in a cache instead (see 16).
</Callout>
