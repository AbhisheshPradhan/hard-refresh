Why ten thousand rows are slow, and the ladder of things to do about it.

"How would you render a list of ten thousand items?" is a common question, and the first move is to reject the premise: find out whether all ten thousand need to be in the browser at all. Usually they do not, and the best answer is server-side filtering with pagination.

When they genuinely do — an inbox, a feed, a data grid — it is worth being precise about what is slow.

## What actually costs

| Cost | Scales with |
|---|---|
| Creating elements and diffing | Item count — real, and usually the smallest part |
| Creating DOM nodes | Item count × nodes per item |
| Layout and paint | Total nodes on the page |
| Memory | Nodes, listeners and their retained data |

Ten thousand cards at fifteen nodes each is 150,000 DOM nodes. React's diff is not the bottleneck; the browser's layout engine is. That is why memoization does not help here, and why the fix is to have fewer nodes rather than to render them more cleverly.

## The ladder

1. **Paginate.** Twenty per page, server-side. Simple, accessible, linkable, and enough for most products.
2. **Load more.** A button that appends the next page. Keeps the user in control and leaves the footer reachable.
3. **Infinite scroll.** The same thing triggered by scrolling. Suits feeds; hostile to almost everything else.
4. **Virtualize.** Render only the visible rows. The answer when all the data must be present at once.
5. **Both.** Virtualized rendering with paged loading. Where large data grids end up.

Climb only as far as the product needs. Each step costs complexity — scroll restoration, keyboard access, testing — and steps four and five cost the most.

## Virtualization

Only the rows in the viewport exist in the DOM, plus a small buffer above and below. A spacer element gives the container the full scroll height so the scrollbar behaves normally.

```jsx
import { useVirtualizer } from '@tanstack/react-virtual';

const JobRows = ({ jobs }) => {
  const parentRef = useRef(null);

  const virtualizer = useVirtualizer({
    count: jobs.length,
    getScrollElement: () => parentRef.current,
    estimateSize: () => 88,
    overscan: 8,
  });

  return (
    <div ref={parentRef} style={{ height: '600px', overflow: 'auto' }}>
      <div style={{ height: `${virtualizer.getTotalSize()}px`, position: 'relative' }}>
        {virtualizer.getVirtualItems().map((row) => (
          <div
            key={jobs[row.index].id}
            ref={virtualizer.measureElement}
            data-index={row.index}
            style={{
              position: 'absolute',
              top: 0,
              transform: `translateY(${row.start}px)`,
              width: '100%',
            }}
          >
            <JobCard job={jobs[row.index]} />
          </div>
        ))}
      </div>
    </div>
  );
};
```

`overscan` renders a few rows beyond the viewport so fast scrolling does not show blank space. `estimateSize` is a guess used before a row is measured; with variable heights, `measureElement` corrects it after render. Uniform heights are considerably simpler, and worth designing for if the content allows.

### Scroll restoration

Navigating into an item and back should return the user to where they were. With virtualization the rows no longer exist, so the browser cannot restore anything by itself. Store the scroll offset — or the top item's index — before navigating away, and call the virtualizer's scroll method after the data is back. Getting this wrong is the most common complaint about virtualized lists.

## Infinite scroll

A sentinel element sits below the last row; when it enters the viewport, load the next page. `IntersectionObserver` does the detection, and it belongs in a hook.

```jsx
export const useIntersection = (ref, onIntersect, enabled = true) => {
  const savedRef = useRef(onIntersect);

  useEffect(() => {
    savedRef.current = onIntersect;
  });

  useEffect(() => {
    if (!enabled || !ref.current) {
      return;
    }

    const observer = new IntersectionObserver((entries) => {
      if (entries[0].isIntersecting) {
        savedRef.current();
      }
    }, { rootMargin: '200px' });

    observer.observe(ref.current);

    return () => {
      observer.disconnect();
    };
  }, [ref, enabled]);
};
```

Two details worth copying. The callback is held in a ref so an inline arrow from the caller does not re-subscribe on every render (see 13). And `rootMargin` triggers the load before the sentinel is visible, so the next page is usually there by the time the user reaches it.

```jsx
const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
  queryKey: ['jobs'],
  queryFn: ({ pageParam }) => {
    return fetchJobs({ cursor: pageParam });
  },
  initialPageParam: null,
  getNextPageParam: (lastPage) => lastPage.nextCursor,
});

useIntersection(sentinelRef, fetchNextPage, hasNextPage && !isFetchingNextPage);

<div ref={sentinelRef} />
{isFetchingNextPage && <Spinner />}
```

The `enabled` guard matters: without it, the observer fires again while a request is in flight and you load the same page several times.

### Cursor versus offset paging

| Offset — `?page=3` | Cursor — `?after=job_482` |
|---|---|
| Easy to implement, jump to any page | Stable when items are added or removed |
| Items shift between pages as data changes, so rows duplicate or vanish | No page numbers, so no jumping to page 40 |
| Slow on large tables | Efficient at any depth |

**Default:** cursors for feeds and anything that changes while the user reads. Offset for stable, finite data where page numbers are part of the interface.

## What infinite scroll costs the user

- The footer becomes unreachable. Anything living there — contact details, legal links — is effectively gone.
- Browser find-in-page only searches rendered rows, so with virtualization it finds almost nothing.
- Keyboard navigation and screen readers need announcements when new items arrive; silently appending content is disorienting.
- Back and forward lose the position unless you restore it deliberately.
- Crawlers may never see content that requires scrolling to load.

These are why "load more" is often the better choice. It has the same loading behaviour, keeps the footer reachable, and gives the user a clear place to stop.

### The cheap option first

Before any of this, `content-visibility: auto` on list items lets the browser skip layout and paint for off-screen content. The nodes still exist, so memory is unchanged, but rendering cost drops considerably for one line of CSS. On a few hundred rows it is often enough.

## Gotchas

- **The cost is DOM nodes, not React.** Memoization does not help a list that is too long.
- **Virtualized rows break find-in-page and anchor links** to items that are not rendered.
- **Without an `enabled` guard, the sentinel fires repeatedly** and loads the same page several times.
- **Offset paging duplicates or skips rows** when the underlying data changes between requests.
- **Scroll restoration must be handled explicitly** once rows are virtualized.
- **Variable row heights are much harder than fixed ones**; design for uniform rows where you can.

## Takeaways

- Ask first whether all the data needs to be in the browser. Usually it does not.
- The cost is DOM nodes, layout and paint — not React's diff.
- Climb the ladder only as far as needed: paginate, load more, infinite scroll, virtualize.
- Virtualization renders a window plus overscan, with a spacer for the full height.
- `IntersectionObserver` in a hook, with a guard so it cannot fire while loading.
- Cursors for changing data; offset for stable data with page numbers.
- Infinite scroll costs the footer, find-in-page, keyboard users and SEO. Default to pagination unless it is a feed.
