A component that renders correctly is not yet an application. An application has URLs, fetches things that fail, and has to keep working when one part of it breaks.

These chapters are about the layer between your components and the outside world. Where data comes from and who caches it. How a URL maps to what is on screen. What happens while something is loading, and what happens when it never arrives. How the whole thing is arranged on disk so a stranger can find anything in it.

The through-line is that each of these is a boundary. A route boundary decides what renders. A Suspense boundary decides what shows while waiting. An error boundary decides how far a failure spreads. Putting them in the right places is most of what application architecture means in React.

<Callout kind="build">
**An application rather than a page**

This is the largest of the six and the one closest to a real codebase.

- Routes for the list, a job detail page, add and edit, a login page, and a not-found route, with a shared layout.
- Filters and pagination in the URL, so a filtered list can be sent to someone.
- Replace hand-rolled fetching with a query library: keys, invalidation after mutations, and one optimistic update.
- A guard layout for the protected routes that handles the unknown-session state correctly on refresh.
- An error boundary per route and one around a widget, each with a retry.
- Restructure into feature folders and check that deleting one feature does not break the others.

Deploy it somewhere static and refresh on a nested URL. If it 404s, chapter 17 told you why.
</Callout>

<Callout kind="note">
**By the end of this part**

You should be able to lay out an application: routes and layouts, data loaded without race conditions or duplicate requests, deliberate loading and error boundaries, protected pages, and a folder structure that still makes sense at fifty components.
</Callout>
